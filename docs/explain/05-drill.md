## Architecture
4. [easy] Walk me through what happens on `casegate run`. — The CLI loads and validates the suite, and fails with exit 2 before any paid call when the YAML is wrong (`src/casegate/loader.py:26-53` `load_suite`). It builds the disk cache and, only when a case needs one, the judge (`src/casegate/cli.py:82-111` `_run_with_judge`). The runner makes one task per (case, repeat) under a semaphore of size C (`src/casegate/runner.py:81-96`). Each task reads the output cache, else calls the target with retries (`src/casegate/runner.py:140-169`), then runs each scorer in order; judge scorers go through `cached_grade` (`src/casegate/judge.py:85-134` `cached_grade`). `aggregate` turns the repeats into case pass rates, the suite pass rate and the std (`src/casegate/stats.py:35-100` `aggregate`). The CLI writes the run JSON and `results/latest.md`, prints the table and exits 0, also when cases fail (`src/casegate/cli.py:156-161`). The gate is a separate command.
5. [medium] What is a Target, and why two adapters? — A Target is the system under test behind a two-method protocol, `run` and `aclose` (`src/casegate/targets/__init__.py:26-29` `Target`). The runner only knows this protocol, so it never cares what is behind it. `PythonTarget` calls an async function in the same process: no server, the fastest path for an agent you own (`src/casegate/targets/python.py:25-32` `run`). `HttpTarget` POSTs each case to a service, so an agent in any language, or a deployed one, can be tested (`src/casegate/targets/http.py:27-39` `run`). Two adapters cover in-process and over-the-network; anything else can be wrapped as a Python function. Trade-off: no plugin system, so a third kind needs a code change.
6. [medium] How does concurrency work, and what does the semaphore bound? — `run_suite` makes one task per (case, repeat) and gathers all of them at once (`src/casegate/runner.py:96`). An `asyncio.Semaphore` of size C (the flag, else the suite's `concurrency`, default 8) lets at most C run (`src/casegate/runner.py:81-82`). The slot covers the whole task: the target call with its retries and, from M2, the judge calls inside scoring. So C bounds all model work in flight, which keeps one run under the API rate limit. The test measures the max tasks in flight with a scripted target (`tests/test_runner.py:136` `test_concurrency_limit`). Trade-off: retry sleeps hold a slot, so a rate-limited run slows down instead of piling on more calls, which is what you want.
7. [hard] How is the pass rate computed with repeats and errors? — A repeat is `error` when the target or a scorer could not finish after retries; it is not a fail (`docs/adr/0003-errors-are-not-failures.md`). A case pass rate is passes over the repeats that did not error, or None when all errored (`src/casegate/stats.py:45-46`). The suite pass rate is the mean of the case pass rates, None cases left out, so each case weighs the same (`src/casegate/stats.py:80`). The std is the sample std of the per-repeat suite pass rates, 0.0 with one repeat (`src/casegate/stats.py:59-67`, `src/casegate/stats.py:81`). Errors are counted on their own in `n_error_repeats`, and the gate limits them separately. On the SPEC §17 fake suite with 3 repeats this gives case rates 1, 0, 1, 1, suite 0.75 and std 0.0 (`tests/test_cli.py:35` `test_run_suite_fake_repeat_3`).
8. [hard] What exactly is in each cache key, and why is the repeat index in it? — The output key is the case input, target version, target model and repeat index (`src/casegate/runner.py:140-146`). The judge key is the whole judge request: system prompt, user prompt, schema name, provider, judge model, effort (Anthropic only), max_tokens and the sample index (`src/casegate/judge.py:100-111`). Both are SHA-256 of canonical JSON (`src/casegate/cache.py:23-29`). The repeat index makes `--repeat 5` five real target calls; without it, five repeats would be one sample read five times and the std would be 0 by construction. Expected values and scorers are not in the output key, so a rubric edit re-grades old outputs and costs only judge calls (`docs/adr/0005-two-caches.md`). The judge key has no repeat index, so the same claim and passage in two repeats share one grade: 7 of 74 judge calls hit on a fresh cache (`evals/baseline.json` `summary.cache_judge_hits`). Trade-off: that hides some judge noise on identical inputs.

12. [hostile] Isn't an LLM judging an LLM circular? — It is circular if you trust the judge without a check, so casegate checks it. `calibrate` joins human pass/fail labels to the judge verdicts in a run and reports agreement and Cohen's kappa, which removes the agreement that chance gives (`src/casegate/calibrate.py:142-180` `calibrate`, `src/casegate/calibrate.py:131-139` `_kappa`). It lists every disagreement with the judge reason, so I can see if the judge is too lenient or too strict. The judge is also a different, larger model than the target (Sonnet 5.5 judges Haiku 5.5, `evals/baseline.json` fields `judge_model` and `target_model`), its prompt is strict, and it takes the median of k samples (`src/casegate/scorers/llm_judge.py:183-190`). Deterministic scorers carry the parts that do not need judgement: tool calls and state. The honest gap: the real kappa on 40 labels is [TBD: `evals/calibration.json`, OPEN-5], and one labeller is a limit (README Limitations). (updated 2026-11-11)
13. [hard] Which decision would you reverse? — The gate runs the action and casegate from the PR head (`.github/workflows/eval-gate.yml:71-73`, `uses: ./`). The baseline, tolerance and must-pass tag are protected (`.github/workflows/eval-gate.yml:51-56`, `.github/workflows/eval-gate.yml:79-82`), but a same-repo PR can still edit `action.yml` or the workflow and so its own gate (SPEC §18.3 Known limit). I would run the gate code from the base ref. The trade-off: a PR that changes `src/` is then judged by the old casegate, so a casegate change is not tested by its own gate. For a portfolio repo with one writer, the risk is small; for a team I would reverse it, or add CODEOWNERS on `.github/` and `evals/`. (updated 2026-11-11)

16. [hard] What happens when the API rate-limits you mid-run? — The target raises a retryable error: an `HttpTarget` turns 429 and 5xx into `HttpStatusRetryable` with the `retry-after` seconds (`src/casegate/targets/http.py:34-35`), and the Anthropic SDK's rate-limit error is classed as retryable (`src/casegate/retry.py:27-44` `is_retryable`). `with_retries` waits the server's hint capped at 30 s, or a backoff of 1, 2, 4 s plus jitter, up to 4 tries (`src/casegate/retry.py:62-88` `with_retries`). The task keeps its semaphore slot while it waits, so the run slows down instead of adding load. If the tries run out, the repeat is `error`, not `fail`, and leaves the pass rate (`src/casegate/runner.py:159-160`). The run file records the try count per repeat (`attempts`); the fake suite proves one repeat with 2 tries (`tests/test_cli.py:35` `test_run_suite_fake_repeat_3`).

## Numbers
17. [easy] What is the pass rate of the example suite, and how was it measured? — 0.973 (`evals/baseline.json` `summary.pass_rate`). 15 cases, 5 repeats each, on a fresh cache folder, never `--no-cache` (SPEC §16.3). Target toy-agent@5 on `claude-haiku-5-5`, judge `claude-sonnet-5-5`. It is the mean of the 15 case pass rates, so each case weighs the same (`src/casegate/stats.py:80`). 13 cases pass 5 of 5; `policy-window-10` and `policy-giftcard-13` pass 4 of 5, both on `citation_support`. Before the toy-agent@5 prompt fix it was 0.867, with all 4 policy cases failing some repeats (`04-failures.md`). 0 error repeats, adversarial cases at 1.0.
18. [medium] What is the run-to-run std, and how did you pick the tolerance? — The per-repeat suite pass rates were 1.000, 1.000, 1.000, 0.933 and 0.933; their sample std is 0.037 (`evals/baseline.json` `summary.per_repeat_pass_rate`, `summary.pass_rate_std`). The tolerance is `max(0.02, ceil(round(2*std*100, 6))/100)` = 0.08 (`evals/tolerance.json` `max_drop`, `docs/adr/0006-gate-tolerance-from-measured-variance.md`). Two std is roughly the band where a noisy run still lands most of the time. The `round(..., 6)` stops float noise from pushing a value like 0.07000000001 up to 0.08. Caveat: 5 points is a small sample for a std. One case that fails all 5 repeats moves the pass rate 0.067, so the gate lets 1 such case through and blocks at 2 (0.133, the doctored test in FACTS.md §8). Before the toy-agent@5 citation fix the std was 0.067 and the tolerance 0.14 (`04-failures.md`).
19. [hard] What is the judge's agreement with human labels, and what is kappa? — Not measured yet: the 40 human labels are a human step (OPEN-5), so the value is [TBD: `evals/calibration.json` `agreement`, `kappa`, `n`]. The method is ready: `casegate calibrate --template --run evals/baseline.json` writes 45 judge rows to label (`evals/labels.template.csv`), and `casegate calibrate --labels evals/labels.csv --run evals/baseline.json --format json` writes the result. On the test fixture, 7 of 10 agree with judge pass 7 and human pass 6, so kappa = (0.7 - 0.54) / (1 - 0.54) = 0.35 (`tests/test_calibrate.py:47` `test_metrics_match_hand_computation`). That fixture shows the formula, not the judge. (updated 2026-11-11)
20. [medium] What does one full run cost, and why is a re-run nearly free? — A cold 15 × 5 run costs $0.193 (`evals/baseline.json` `summary.cost_usd_full`), target and judge together, at prices dated 2026-11-03. A re-run on the same cache folder hit 75 of 75 outputs and 74 of 74 grades and cost $0.0000 (FACTS.md §8). Both costs are in every run: `cost_usd` counts a cache hit as 0, `cost_usd_full` counts it at its original price (`src/casegate/runner.py:181-193`). A rubric edit is cheap too: the outputs stay cached and only the judge calls for that rubric run again. The whole M2 build spent about $0.81 of a $2 budget (FACTS.md §8).

## System design at 10x
21. [hard] 10x the cases: what breaks first? — Cost and time per PR, then the API rate limit. 150 cases × 5 repeats is 750 tasks; cost grows with tasks, so about 10 × $0.193 per cold run (`evals/baseline.json` `summary.cost_usd_full`, scaled by hand, not measured). The semaphore holds concurrency at 8 (`src/casegate/runner.py:82`), so wall time grows too, and more 429s mean more retries (`src/casegate/retry.py:68-79`). The output does not break: the terminal shows the worst 20 cases (`src/casegate/console.py:38`) and compare keeps the 10 largest deltas (`src/casegate/compare.py:27`). One thing improves: more cases give a smaller std, so the measured tolerance gets tighter (`docs/adr/0006-gate-tolerance-from-measured-variance.md`). I would run a tagged subset per PR (`--tag`, `src/casegate/cli.py:117`) and the full suite on `main`. (updated 2026-11-11)
22. [hard] 10x the PRs per day: how do you control cost? — Four levers exist now. Path filters run the gate only when agent, eval, source or action files change (`.github/workflows/eval-gate.yml:6-11`). A new push cancels the old PR run (`.github/workflows/eval-gate.yml:26-28`). A fork PR with no secret skips at $0 (`.github/workflows/eval-gate.yml:36-41`). The output cache key includes `target.version`, so a PR that does not touch the agent could reuse outputs (`docs/adr/0005-two-caches.md`). At 10x I would persist `CASEGATE_CACHE_DIR` between CI runs with `actions/cache` keyed on `target.version`; today CI starts cold, about $0.27 per PR (BUILD.md cost model, an estimate). The risk: the cache trusts the version, so a code change without a bump reuses stale outputs (README Limitations). (updated 2026-11-11)
23. [hostile] Your gate blocked a good PR because of judge noise. What now? — First I read the comment: it lists each pass-to-fail flip with the failing scorer and reason (`src/casegate/compare.py:84-137` `compare`). If every flip is a judge scorer and the reasons are borderline, it is noise, not the agent. A rerun until green is the wrong habit, because it turns the gate into a coin toss. The fixes are structural: re-measure the std and the tolerance (BUILD.md runbook, `docs/adr/0006-gate-tolerance-from-measured-variance.md`), raise the judge samples k for that case (`src/casegate/scorers/llm_judge.py:51`), or tighten the rubric after `calibrate` shows the judge disagrees with people there. The tolerance is 0.08 because one flip in 15 moves a repeat by 0.067 (`evals/tolerance.json` `max_drop`, `evals/baseline.json` `summary.per_repeat_pass_rate`). A must-pass case has no tolerance on purpose: an adversarial case that fails once is a real block. (updated 2026-11-11)
24. [hard] How would you run this against a production agent behind an API? — Use the HTTP target: `target: {type: http, url: ..., headers: {Authorization: "Bearer ${TOKEN}"}, version: ...}`. casegate POSTs `{case_id, input}` per case and expects an `Output` JSON back (`src/casegate/targets/http.py:30-39`). The token stays out of `suite.yaml`: `${TOKEN}` is read from the environment at load, and a missing one is a load error (`src/casegate/targets/__init__.py:56-72` `_expand_headers`). 429 and 5xx retry; other 4xx fail fast as errors (`src/casegate/targets/http.py:34-37`). The service must report its tool calls and state in the Output, or trajectory and state scoring have nothing to read; that is the real integration work. I would point it at staging with fake data, because the cases run real tool calls.

## Brief talking points
25. [medium] Why does trajectory scoring matter more than final-answer scoring for agents? — An agent can say "your refund of $39 is done" without looking up the order, or after calling the wrong tool. Case `refund-within-cap-01` checks three things (`evals/cases/01-refund-within-cap-01.yaml`). The trajectory: `get_account`, then `get_order`, then `issue_refund` with `amount <= 39`, in that order, and `escalate` is forbidden (`src/casegate/scorers/tool_trajectory.py:122-130`). The state: order 1042 is `refunded` (`src/casegate/scorers/state_match.py:85-104` `score`). The reply: the judge checks it confirms the amount and promises no timeline. The adversarial case `refund-over-cap-adv` goes further: the store logs refused refund attempts, so a $390 try fails the case even though the store blocked it (`examples/toy_agent/store.py:184-188`). A final-answer check would pass that agent. In the baseline both cases pass 5 of 5 (`evals/baseline.json`).
26. [hard] How did you decide the gate tolerance given run-to-run variance? — I measured it instead of picking a number. With 15 cases one flip moves the pass rate 6.7 points, so the brief's 0.03 would fail on noise (`docs/adr/0006-gate-tolerance-from-measured-variance.md`). The baseline ran 5 times on a fresh cache; the std of the 5 suite pass rates is 0.037 (`evals/baseline.json` `summary.pass_rate_std`). Two std, rounded up to the next 0.01, with a floor of 0.02, gives 0.08 (`evals/tolerance.json`). The floor stops a std of 0 giving a zero tolerance. The average is not the only guard: the gate also blocks on any error repeat and on any adversarial case that misses one repeat (`src/casegate/gate.py:77-113` `gate`). The honest limit: 0.08 is still wide on 15 cases; more cases would shrink the noise, and a paired per-case test is the next step.
27. [hard] One case where the judge was wrong, and how calibration exposed it. — The clear case came before calibration: the judge gave 0.8, 0.85 and 0.8 to a reply that only offered a refund once eligibility was confirmed, for a rubric that asks for a confirmed refund (FACTS.md §4.2). A person says fail; the judge said pass. That one case is why the judge prompt now has a hedging rule and score anchors (`src/casegate/scorers/llm_judge.py:24-42` `JUDGE_SYSTEM`, `04-failures.md`). Calibration makes that check systematic: each disagreement row shows the judge value, the human verdict and the judge reason (`src/casegate/calibrate_md.py:34-44` `disagreement_cells`). The disagreements on the real 40 labels are [TBD: `evals/calibration.json` `disagreements`, OPEN-5]. (updated 2026-11-11)

## Code
28. [medium] Show me how a tool-trajectory subsequence match works. — It walks the actual calls once with a pointer into the expected list; each call that matches the current expected spec moves the pointer (`src/casegate/scorers/tool_trajectory.py:122-130`). A match needs the same name and every listed arg to pass its matcher, for example `amount: {lte: 39}` (`src/casegate/scorers/tool_trajectory.py:71-74` `_matches`). Extra calls in between are fine. The value is matched over expected, and the reason names the first unmatched spec. Example: expected `get_account → get_order`, actual `get_order, get_account, get_order` gives 1.0; actual `get_order, get_account` gives 0.5. Ignored tools leave the comparison, but a forbidden call anywhere sets the value to 0 (`src/casegate/scorers/tool_trajectory.py:151-153`). Greedy is correct here: the earliest match always leaves the most calls for later specs.
29. [medium] How does the gate stop a PR from lowering its own baseline? — `02-decisions.md` (ADR 0008).
30. [hostile] Why should I trust your numbers? — Every number is in `03-numbers.md` with its source file, its field and the command that makes it. A number with no file is written as TBD, not guessed; the calibration row is TBD today for that reason. A script fails CI when a numbers row names a file that does not exist (`scripts/check_explain.py:55-79`). The baseline is a committed file, and run files that were replaced are archived in `docs/assets/runs/`. The numbers are also small on purpose: 15 cases × 5 repeats and one labeller, and the README says so in Limitations. Do not trust the toy suite as a claim about a real agent; trust the method. (updated 2026-11-11)

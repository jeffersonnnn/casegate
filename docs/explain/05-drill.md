## Architecture
4. [easy] Walk me through what happens on `casegate run`. — The CLI loads and validates the suite, and fails with exit 2 before any paid call when the YAML is wrong (`src/casegate/loader.py:26-53` `load_suite`). It builds the disk cache and, only when a case needs one, the judge (`src/casegate/cli.py:79-108` `_run_with_judge`). The runner makes one task per (case, repeat) under a semaphore of size C (`src/casegate/runner.py:81-96`). Each task reads the output cache, else calls the target with retries (`src/casegate/runner.py:140-169`), then runs each scorer in order; judge scorers go through `cached_grade` (`src/casegate/judge.py:85-134` `cached_grade`). `aggregate` turns the repeats into case pass rates, the suite pass rate and the std (`src/casegate/stats.py:35-100` `aggregate`). The CLI writes the run JSON and `results/latest.md`, prints the table and exits 0, also when cases fail (`src/casegate/cli.py:153-158`). The gate is a separate command.
5. [medium] What is a Target, and why two adapters? — A Target is the system under test behind a two-method protocol, `run` and `aclose` (`src/casegate/targets/__init__.py:26-29` `Target`). The runner only knows this protocol, so it never cares what is behind it. `PythonTarget` calls an async function in the same process: no server, the fastest path for an agent you own (`src/casegate/targets/python.py:25-32` `run`). `HttpTarget` POSTs each case to a service, so an agent in any language, or a deployed one, can be tested (`src/casegate/targets/http.py:27-39` `run`). Two adapters cover in-process and over-the-network; anything else can be wrapped as a Python function. Trade-off: no plugin system, so a third kind needs a code change.
6. [medium] How does concurrency work, and what does the semaphore bound? — `run_suite` makes one task per (case, repeat) and gathers all of them at once (`src/casegate/runner.py:96`). An `asyncio.Semaphore` of size C (the flag, else the suite's `concurrency`, default 8) lets at most C run (`src/casegate/runner.py:81-82`). The slot covers the whole task: the target call with its retries and, from M2, the judge calls inside scoring. So C bounds all model work in flight, which keeps one run under the API rate limit. The test measures the max tasks in flight with a scripted target (`tests/test_runner.py:136` `test_concurrency_limit`). Trade-off: retry sleeps hold a slot, so a rate-limited run slows down instead of piling on more calls, which is what you want.
7. [hard] How is the pass rate computed with repeats and errors? — A repeat is `error` when the target or a scorer could not finish after retries; it is not a fail (`docs/adr/0003-errors-are-not-failures.md`). A case pass rate is passes over the repeats that did not error, or None when all errored (`src/casegate/stats.py:45-46`). The suite pass rate is the mean of the case pass rates, None cases left out, so each case weighs the same (`src/casegate/stats.py:80`). The std is the sample std of the per-repeat suite pass rates, 0.0 with one repeat (`src/casegate/stats.py:59-67`, `src/casegate/stats.py:81`). Errors are counted on their own in `n_error_repeats`, and the gate limits them separately. On the SPEC §17 fake suite with 3 repeats this gives case rates 1, 0, 1, 1, suite 0.75 and std 0.0 (`tests/test_cli.py:35` `test_run_suite_fake_repeat_3`).
8. [hard] What exactly is in each cache key, and why is the repeat index in it? — The output key is the case input, target version, target model and repeat index (`src/casegate/runner.py:140-146`). The judge key is the whole judge request: system prompt, user prompt, schema name, provider, judge model, effort (Anthropic only), max_tokens and the sample index (`src/casegate/judge.py:100-111`). Both are SHA-256 of canonical JSON (`src/casegate/cache.py:23-29`). The repeat index makes `--repeat 5` five real target calls; without it, five repeats would be one sample read five times and the std would be 0 by construction. Expected values and scorers are not in the output key, so a rubric edit re-grades old outputs and costs only judge calls (`docs/adr/0005-two-caches.md`). The judge key has no repeat index, so the same claim and passage in two repeats share one grade: 7 of 74 judge calls hit on a fresh cache (`evals/baseline.json` `summary.cache_judge_hits`). Trade-off: that hides some judge noise on identical inputs.

16. [hard] What happens when the API rate-limits you mid-run? — The target raises a retryable error: an `HttpTarget` turns 429 and 5xx into `HttpStatusRetryable` with the `retry-after` seconds (`src/casegate/targets/http.py:34-35`), and the Anthropic SDK's rate-limit error is classed as retryable (`src/casegate/retry.py:27-44` `is_retryable`). `with_retries` waits the server's hint capped at 30 s, or a backoff of 1, 2, 4 s plus jitter, up to 4 tries (`src/casegate/retry.py:62-88` `with_retries`). The task keeps its semaphore slot while it waits, so the run slows down instead of adding load. If the tries run out, the repeat is `error`, not `fail`, and leaves the pass rate (`src/casegate/runner.py:159-160`). The run file records the try count per repeat (`attempts`); the fake suite proves one repeat with 2 tries (`tests/test_cli.py:35` `test_run_suite_fake_repeat_3`).

## Numbers
17. [easy] What is the pass rate of the example suite, and how was it measured? — 0.973 (`evals/baseline.json` `summary.pass_rate`). 15 cases, 5 repeats each, on a fresh cache folder, never `--no-cache` (SPEC §16.3). Target toy-agent@5 on `claude-haiku-5-5`, judge `claude-sonnet-5-5`. It is the mean of the 15 case pass rates, so each case weighs the same (`src/casegate/stats.py:80`). 13 cases pass 5 of 5; `policy-window-10` and `policy-giftcard-13` pass 4 of 5, both on `citation_support`. Before the toy-agent@5 prompt fix it was 0.867, with all 4 policy cases failing some repeats (`04-failures.md`). 0 error repeats, adversarial cases at 1.0.
18. [medium] What is the run-to-run std, and how did you pick the tolerance? — The per-repeat suite pass rates were 1.000, 1.000, 1.000, 0.933 and 0.933; their sample std is 0.037 (`evals/baseline.json` `summary.per_repeat_pass_rate`, `summary.pass_rate_std`). The tolerance is `max(0.02, ceil(round(2*std*100, 6))/100)` = 0.08 (`evals/tolerance.json` `max_drop`, `docs/adr/0006-gate-tolerance-from-measured-variance.md`). Two std is roughly the band where a noisy run still lands most of the time. The `round(..., 6)` stops float noise from pushing a value like 0.07000000001 up to 0.08. Caveat: 5 points is a small sample for a std. One case that fails all 5 repeats moves the pass rate 0.067, so the gate lets 1 such case through and blocks at 2 (0.133, the doctored test in FACTS.md §8). Before the toy-agent@5 citation fix the std was 0.067 and the tolerance 0.14 (`04-failures.md`).

[hard] How would you run this against a production agent behind an API? — Use the HTTP target: `target: {type: http, url: ..., headers: {Authorization: "Bearer ${TOKEN}"}, version: ...}`. casegate POSTs `{case_id, input}` per case and expects an `Output` JSON back (`src/casegate/targets/http.py:30-39`). The token stays out of `suite.yaml`: `${TOKEN}` is read from the environment at load, and a missing one is a load error (`src/casegate/targets/__init__.py:56-72` `_expand_headers`). 429 and 5xx retry; other 4xx fail fast as errors (`src/casegate/targets/http.py:34-37`). The service must report its tool calls and state in the Output, or trajectory and state scoring have nothing to read; that is the real integration work. I would point it at staging with fake data, because the cases run real tool calls.

## Brief talking points
25. [medium] Why does trajectory scoring matter more than final-answer scoring for agents? — An agent can say "your refund of $39 is done" without looking up the order, or after calling the wrong tool. Case `refund-within-cap-01` checks three things (`evals/cases/01-refund-within-cap-01.yaml`). The trajectory: `get_account`, then `get_order`, then `issue_refund` with `amount <= 39`, in that order, and `escalate` is forbidden (`src/casegate/scorers/tool_trajectory.py:122-130`). The state: order 1042 is `refunded` (`src/casegate/scorers/state_match.py:85-104` `score`). The reply: the judge checks it confirms the amount and promises no timeline. The adversarial case `refund-over-cap-adv` goes further: the store logs refused refund attempts, so a $390 try fails the case even though the store blocked it (`examples/toy_agent/store.py:184-188`). A final-answer check would pass that agent. In the baseline both cases pass 5 of 5 (`evals/baseline.json`).
26. [hard] How did you decide the gate tolerance given run-to-run variance? — I measured it instead of picking a number. With 15 cases one flip moves the pass rate 6.7 points, so the brief's 0.03 would fail on noise (`docs/adr/0006-gate-tolerance-from-measured-variance.md`). The baseline ran 5 times on a fresh cache; the std of the 5 suite pass rates is 0.037 (`evals/baseline.json` `summary.pass_rate_std`). Two std, rounded up to the next 0.01, with a floor of 0.02, gives 0.08 (`evals/tolerance.json`). The floor stops a std of 0 giving a zero tolerance. The average is not the only guard: the gate also blocks on any error repeat and on any adversarial case that misses one repeat (`src/casegate/gate.py:77-113` `gate`). The honest limit: 0.08 is still wide on 15 cases; more cases would shrink the noise, and a paired per-case test is the next step.

## Code
28. [medium] Show me how a tool-trajectory subsequence match works. — It walks the actual calls once with a pointer into the expected list; each call that matches the current expected spec moves the pointer (`src/casegate/scorers/tool_trajectory.py:122-130`). A match needs the same name and every listed arg to pass its matcher, for example `amount: {lte: 39}` (`src/casegate/scorers/tool_trajectory.py:71-74` `_matches`). Extra calls in between are fine. The value is matched over expected, and the reason names the first unmatched spec. Example: expected `get_account → get_order`, actual `get_order, get_account, get_order` gives 1.0; actual `get_order, get_account` gives 0.5. Ignored tools leave the comparison, but a forbidden call anywhere sets the value to 0 (`src/casegate/scorers/tool_trajectory.py:151-153`). Greedy is correct here: the earliest match always leaves the most calls for later specs.
